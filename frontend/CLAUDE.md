# frontend/ — Vite + React + Recharts

Loaded when working under `frontend/`. Moved out of the root CLAUDE.md so it costs no
context in a backend-only session; the project-wide charters (privacy, surface-don't-
diagnose, the YYYY-MM-DD date rule) still live in the root file and apply here too.

Vite + React (JavaScript) + Recharts. `src/api.js` is the only thing that talks to the backend (base URL from `VITE_API_BASE` in `.env`); its `sendJSON` write helper throws an error carrying `.status` and the backend's `detail` on `.message`, and backs `addObservation`/`updateObservation`/`deleteObservation`. `App.jsx` owns state and the loading/empty/error branches, plus a `reloadKey` it bumps to force a series/flags refetch after any add/edit/delete; it re-fetches `/metrics` after add and delete (so metrics appear/vanish correctly), splitting that response into a metric-name array and a `unitByMetric` map, and holds the `editing` row. `ObservationForm.jsx` is always rendered (so a reading can be added to an empty DB) and is **reused for both add and edit** — in edit mode it's pre-filled (remounted via `key`), the metric is locked, and submit routes to PUT. A **result-type selector** (Numeric / Qualitative / Censored) reshapes the form: numeric shows value + ref_low/ref_high; qualitative shows a result-text field **and a `normal_text` expected-normal field** (both free-text `datalist`s; ref hidden, unit optional); censored shows an operator select (`<`,`>`,`<=`,`>=`) + value **and ref_low/ref_high as its expected-normal** (a censored normal is numeric, e.g. `<5` with normal `<=10` → ref_high 10). **Validation branches by type** (qualitative needs only result-text; censored needs operator + numeric value + unit; numeric keeps value-numeric + ref_low ≤ ref_high) — numeric rules never apply to the non-numeric paths. The unit field auto-fills and locks once the metric is a known one (from `unitByMetric`), independent of result-type, so a metric can legitimately hold a **mix** of numeric/censored/qualitative readings (e.g. a viral load with `<20` and plain numbers) and the unit stays consistent. **Edit is type-locked to the row's existing type** (the selector is disabled in edit mode; only numeric rows are editable since `ObservationTable` disables Edit on non-numeric ones) — changing a reading's type means delete + re-add. On a write conflict it surfaces the backend's `detail` message (duplicate date or unit mismatch). `ObservationTable.jsx` lists the selected metric's readings below the chart with edit and a **two-step inline delete** (Delete → Confirm/Cancel, no one-click). (`SummaryPanel.jsx` — the on-demand "Explain these findings" narration button — was **REMOVED** in a QoL cleanup alongside the Ollama summarizer; `/summary` still exists and narrates via the on-device template, but has no UI trigger now.) `PdfImport.jsx` (in the always-rendered entry area, below `ObservationForm`) uploads a PDF to `/import/pdf` and shows the draft as an **editable review table** — every field editable, rows removable, a per-row **source badge** (`text` vs an amber `OCR ⚠ verify`), and a document banner that warns when OCR was used so scanned values aren't trusted like clean text. **Nothing saves until approved**: it posts the approved rows to `/observations/import` and shows per-row results (saved ✓ / the duplicate or unit-mismatch error), keeping failed rows editable to fix and re-save; on any save it calls `onImported` to refresh metrics + series. `MetricChart.jsx` draws a **stepped reference band** as per-segment `<ReferenceArea>`s in a `ComposedChart` (the earlier `<Area>`+`stepAfter` band and its I-beam `ErrorBar` were retired in `fb8ef65`): consecutive readings sharing a range shape become one run, each rendered as a rect that steps at the MIDPOINT where the range changes; a both-bounds run is a solid `[ref_low, ref_high]`, a one-sided run is solid at its present bound and fades (gradient) to the domain edge, and a no-range reading emits nothing (a gap). The band is **fill-only** (`fillOpacity 0.2`, `stroke="none"`) — the crisp per-bound edge lines that used to outline each `ref_low`/`ref_high` were removed. The Y-domain folds in every displayed range so no segment clips. Flag→point mapping is **by `observed_on`**: the backend stamps each point-level flag with its reading's date (`out_of_range` is judged per reading against its own range), so the chart maps them to exact points — out-of-range = solid red dot; noteworthy-but-in-range (`personal_baseline`/`delta`/`threshold`) = uniform dot with a small amber caret above; red takes precedence; `trend` now carries the latest reading's date (so every flag has a date for the list) but still highlights no chart point — the chart maps carets by KIND (`personal_baseline`/`delta`/`threshold`) and `trend` isn't among them. `MetricChart` charts **numeric AND censored readings**: numeric points drive the trend line + dots (the value `Line` uses `connectNulls` to bridge over censored dates), while censored readings (`result_type === 'censored'`) render on a **separate `Line dataKey="censored"` layer** as a small muted-grey **capped-arrow** at their bound — down for `<`/`<=` ("at or below"), up for `>`/`>=` ("at or above"), with a tooltip like `<5 mg/dL — at or below the limit`. The chart Y-domain folds in censored bounds (rendering-only, so the arrow is never off-screen; the engine still excludes censored from all math). Censored readings shade the stepped band by the **same per-reading rule** as numeric ones (their own range, gap if absent). **Chart-gating rule:** a chart renders only when the metric has **≥1 numeric observation** (`result_type === 'numeric'` with a non-null `value`); the render-gate predicate matches the `charted` filter's numeric condition **exactly**, so the gate and the plot filter can't diverge. Censored rows **no longer trigger a chart on their own** (the gate was previously numeric-OR-censored, which drew arrows on a bare time axis for a censored-only metric); a metric with zero numeric rows now shows the empty-state note ("no numeric readings to chart") instead. But once a numeric reading brings the chart up, censored rows on that **mixed** metric **still plot as arrow glyphs** exactly as before — this rule changed the render/no-render gate only, not what's drawn once the chart is up. Qualitative and range-as-text values have no Y position and stay **"not charted"** (a dedicated `range` result type to chart microscopy values like `0-5` was considered and **dropped** — not worth the result-type / storage / migration cost; those values stay stored as-is, visible in the table/timeline, excluded from charts). This keeps the chart **honest**: it routes rows by their declared `result_type` and **never coerces** a censored/qualitative value into a numeric point — non-numeric values are never charted but are always visible in the table/timeline. **Design tokens live in `src/index.css`'s `:root`** — `--c-accent` (graphite) and its strong/soft/line variants, `--c-baseline` (the personal-baseline violet, deliberately NOT the accent: it marks one feature and must stay distinct), plus the type stacks `--font-body` / `--font-display` (Bahnschrift) / `--font-serif` (Sitka) / `--font-num` (Cascadia Mono). They replaced ~90 hardcoded violet hexes, so a palette change is now an edit in one place. Two rules: **semantic colours are NOT tokenised** (red = out of range, green = the reference band, amber = worth a look — they carry meaning and must not follow the theme), and **fonts are system faces only, never a CDN** — a webfont link is an external request on every page load, which the privacy charter rules out. Recharts takes colours as props and can't read a CSS variable, so the chart's accent constants live in **`src/theme.js`**, which names the token each mirrors; keep the two in sync. The shared inline SVGs (`components/icons.jsx`) now draw with `currentColor` and get their colour from `.baseline__icon`.

The Metrics page is **a sticky metric RAIL + the RECORD** (`.metric` grid). The rail names the metric (its own `h2` — the page has no "Metrics" title, which used to sit above a picker naming the same thing), states unit, latest reading, drawn date, interval and reading count, and holds both actions: `+ Add reading` and a `Manage metric ▾` menu (`components/ActionMenu.jsx` — a dependency-free menu in the Modal/NavDrawer house style: role="menu", Esc + click-outside to close, arrow-key item nav) carrying the per-metric settings (display name / unit / group) and the two export toggles as `menuitemcheckbox`es. The rail's facts render through `readingFormat.js`'s `valueOnly`/`displayNormal` — the readings table's own formatters, extracted to a plain module (a component file may only export components) so the same reading can't be formatted two ways. The record column drops all card chrome: `.rsec__head` gives each section a display-face label with a hairline running to the right margin, and `.metric__record` strips the border/background off `.chart`, `.readings` and `.flag`. The column divider hangs off the RECORD, not the rail — the rail is sticky and only as tall as its own content, so a border there stopped partway down the page. **`FlagList` and `HistoryPanel` share ONE white panel and ONE scroll** (`.findings`, capped at 30rem) instead of sitting side by side (`.findings-row` is unused by this page now): they're two views of the same question, the record column is half the old page width, and a long history would otherwise push the readings table out of reach. Each list keeps its own heading, **stuck to the top of the shared scroll area** so you can see which of the two you're reading — which is why the panel has NO top padding: a gap above a sticky heading is a strip that rows visibly scroll through. **The chart legend + guideline definitions moved BELOW the readings table** — reference material you consult, not something to scan on the way to the numbers: `MetricChart` takes `legend={false}` and the page renders `<ChartLegend>` itself. `ChartLegend.jsx` re-derives its own conditions from `series`/`flags` through the shared `chartRows.js` helpers (`chartableRows`, `hasBand` — also used by MetricChart, so the two can't drift) rather than being handed the chart's internals; `legend` defaults to true, so every other caller (the weight chart) is unchanged. **The rail is its own scroll pane** — a FIXED height (`100vh` minus the header), `overflow-y: auto`, `overscroll-behavior: contain` — so it scrolls independently of the record beside it. A `max-height` was not enough: at that size it only became a pane once its content happened to overflow, and otherwise moved with the page. **`BaselineMode`'s "turn it on" trigger is a Manage-metric MENU ITEM**, not a rail callout: it was only ever a trigger and it showed on most metrics at rest. The component now renders just two states — mode ON (the active callout, which carries the note editor) and the SUGGESTION banner (an active pitch that has to be seen, so it stays on the page). Because the menu item and the callout are two views of ONE setting, **the page owns it**: `MetricsPage` fetches `getMetricSettings` and passes `data` + `onApply` down, and the fetched settings are TAGGED with the metric they belong to (`{ metric, ...settings }`, checked at the render site) — the same self-correcting pattern `chartDomain` uses, which also avoids a reset-state-in-effect. **The metric's notices live in the rail**, under the picker, beside the identity they qualify — the advisory ("not a standard test"), the derived "computed from …" caption, the methodology "read with …" note, and `BaselineMode`'s control. They share ONE shape (`.notice`: a filled tint darker than the page, a left rule, a small display-face label on its own line, text flush beneath): a warning differs by colour and wording, never by layout. **The rail's caution colour is the chart's noteworthy amber** (`#f59f00`) — the warning notice and the personal-baseline callout both take it, so the rail speaks in one accent instead of three. Note the tension: amber elsewhere means "worth a look", and the baseline callout is a status rather than a caution; if it ever reads as a warning, that rule is where to change it. **The chart keeps a panel** (white, hairline border) while the readings table stays unboxed — a chart is a drawing with its own coordinate space and the box says where that space ends; the table's rules already do that job. **Point marks are semantic, not theme** (`OUT_OF_RANGE` / `NOTEWORTHY` in MetricChart): out-of-range is a small red dot, noteworthy-but-in-range a SOLID amber triangle pointing DOWN at its reading (an outline at that size reads as a smudge), and `activeDot` is customised so a hovered out-of-range point **stays red** — Recharts' default hover dot paints in the LINE's colour, which turned the mark graphite exactly when you pointed at it to read it. The old advisory put a ⚠ in a flex row that indented its text while the captions beside it sat flush, so two notes about the same metric disagreed about where their left edge was — hence the label line instead of an icon. `.app`'s `max-width` went 820px → **1180px**: 820 was sized for one column of cards, and left the record column ~500px to hold a chart, a table and a legend. **The rail sticks BELOW the app header, which is itself `sticky; top: 0` and opaque** — at `top: 0.5rem` the rail slid under it and lost its name, unit and picker the moment the page scrolled, so the offset is `calc(var(--app-header-h) + 0.75rem)`. **A sticky column taller than the viewport can never be scrolled to its own bottom** (the page scrolls past while it stays pinned), so the rail caps its height and scrolls internally. That overflow would clip a popup, which is why **`ActionMenu` portals its menu to `<body>` and positions it `fixed`** against the trigger's rect: it measures on open, flips upward when there's no room below, caps its height, and clamps horizontally to the viewport — all written to the DOM node directly, since it's measurement, not state. Two consequences the portal forces: the outside-click handler must test the menu node *separately* from the wrapper (the menu is no longer inside it, and closing on mousedown would otherwise unmount an item before its own click ran), and any scroll closes the menu, since a fixed popup cannot follow its trigger. **Home is the same language on a two-column grid** (`.home`): a full-width header — at-a-glance counts (metrics tracked / flagged now / moved in N days) on the left, the page's ONE primary action on the right — then a wide MAIN column for the weight chart (a chart uses the width) and a narrower SIDE column for the digest and the flag list (text that reads fine in a shorter measure). The side column IS a `.findings` panel — the same white, capped, single-scroll container the Metrics page uses — so the digest and the flag list read as one box with each heading pinned as its rows scroll under it. `.ovlist` keeps its own 26rem cap for when it is NOT inside that panel, and `.findings .ovlist` drops it: two nested scroll areas in one box is a trap, where the outer looks finished while the inner still has rows. One column below 900px, where a ~300px side column is too narrow for a chart. **The full-picture export is a header BUTTON**, matching `+ Add reading` on the Metrics page: it toggles `ExportPanel` in `autoStart` mode (the same mode `MultiExportControls` uses — the panel skips its own trigger and opens straight into the preview) rendered **full width** directly beneath, because the preview is a wide table of everything about to leave the machine and reading it is the safety step. `.metrics__add` was renamed `.btn-primary` — it's the app's single primary-button style, and there should never be two competing in one view. **The large buttons are a SQUARED PLATE**: `.btn-primary`, `.metrics__rename` and `.menu__button` share one rule for shape, size and type — the display face, uppercase, `letter-spacing: .1em`, 3px corners — which is deliberately the same treatment as `.rsec__head` and the metric tags, so a button reads as part of the record's type system rather than a web control dropped onto a document. The tracking is what carries the emphasis, which is why the primary needs no shadow and the secondary needs no fill; only the fill and border colour separate the three, and the secondary carries a border of the SAME width as the primary's (which borders itself in its own fill) so a stacked pair comes out the same height. Two knock-ons this style forces: `.readings__actions button` now has to unwind `text-transform`/`letter-spacing`/`font-weight`, because Collections' row-level Edit reuses `.metrics__rename` and would otherwise shout where its neighbours whisper; and Timeline's header row aligns `stretch` rather than `center`, so the list/calendar toggle (sized by its icons) matches the button's plate instead of hardcoding a height. `.menu__button--icon` repeats only the vertical padding, so an icon trigger and a labelled one are the same height side by side. The **page owns the `/overview` and `/changes` fetches** and passes the payloads down, because both endpoints return `total_metrics` and the counts strip spans both; two independent fetches could disagree. Order is deliberate — what stands out, then what changed, then weight, then the export; the weight chart used to open the page, which led with the least urgent thing. **`.stat` / `.stat__k` / `.stat__v` / `.stat__hero` / `.stat__big` / `.stat__unit` are the shared "labelled fact" vocabulary** (renamed from `.metric__*`): the metric rail, Home's counts strip and the weight chart's header all use them, so a figure looks the same wherever it appears. One leftover to know about: the export block keeps its violet rule — it's the only violet chrome left, and it marks the surface where data leaves the machine, so it was left alone rather than flattened into the accent. **The X axis picks its scale before its ticks** (`chartTime.js`'s `axisTicks`, the single entry point both `MetricChart` and `QualitativeTimeline` call — returning `{ ticks, step }` together so a caller can't pair a step with ticks computed for a different one). Month boundaries first, and **a month tick wins as soon as ONE lands**; only a span holding NO month boundary at all falls to **day-aligned ticks anchored on the Monday at or before the first reading**, so a weekly gridline lands on a week start. The threshold has moved twice and it is worth being precise about why. The original defect was the LABEL, not the count: a series running 2026-06-21 → 2026-07-27 holds exactly one month boundary, the `>= 2` test rejected it, and the fallback drew gridlines at the first and last READING while still labelling them "Jun 2026"/"Jul 2026" — two lines claiming to be month starts that were nothing of the kind (observed on Home's weight chart). The first fix sent that span to the day tier, which traded two false month lines for five true week lines on a chart whose gridlines are meant to mark months; `>= 1` is the direct fix, and that span now draws ONE gridline, at the real 1st. Sparse but true beats dense and off-topic. Formatting follows the step, which is also how the date charter is satisfied: a month/year tick is a PERIOD label (the charter's one exception), a day tick is a specific date and renders `YYYY-MM-DD`. A single-reading series keeps the endpoint fallback and now labels it with its actual date rather than a month it merely falls inside. **Timeline** carries the same vocabulary: the page title in the serif that names a metric, month group headers (and the calendar's year labels) as display-face section heads with the hairline rule running out to the margin, mono tabular dates and reading values, `.btn-primary` for "+ Add event", and panel chrome (`--c-line`, 4px) on entry cards and calendar cells. Its list/calendar switch was a grey track with a sliding white thumb; it is now **the same segmented control as the chart's Linear/Log switch** — hairline box, active segment filled with the accent — because two idioms for one kind of choice is the inconsistency this pass exists to remove. Per-kind colours (condition green, lab crimson, …) are untouched: they encode which source an entry came from, so they aren't the theme's to change. **The kind filters and the sort control share one rule** — the large buttons' squared plate scaled down (display face, uppercase, tracked, 3px) — because they are one set of controls on one row; the filter's on-state still keys to `--kind` rather than the accent, since it answers "which sources am I seeing" and matches its own entry dot. The entry TAG stays a pill: a plate is a control, a pill is a label, and both appear in this view. **Entry body type sits a step below the entry's head row**: titles/links 0.86rem, notes 0.8rem, a lab row's metric and value 0.86rem — the head (tag, date, subtype) is deliberately untouched, so scanning down the list follows the dates rather than the prose. One trap that rule hit: `.tl-reading` sets `font: inherit`, whose shorthand RESETS font-size to the body's, which made a lab row's metric name the largest text in its own entry — the size therefore has to be re-declared AFTER the shorthand. `CalendarViewIcon` also overrides the shared 2px `strokeWidth` with 1.6: it carries more geometry than its siblings (frame, header rule, two hangers, five dots) and read as a heavier block than the list icon beside it in the same toggle. **Forms are ONE style, app-wide** (`.form` — the add/edit reading modal, the metric modals, an event, a condition, a profile measurement): a form that looked different per page is the same inconsistency this pass exists to remove. A field LABEL is the `.stat__k` / `.rsec__head` head (display face, uppercase, tracked) and the value inside it returns to the body face — which works here because these labels are one or two words ("Metric", "Ref low") and does NOT work in Settings, where a label is a full phrase and tracked uppercase turns reading into decoding. Number and date inputs take the mono face, so the value you type matches the value you read back in the table. Two specificity traps this style set: `.form label` matches the checkbox row too, so `.form__check` has to carry the element in its selector (`.form label.form__check`) or every reset it declares is lost — and again for its checkbox, which the full-width-control rule would otherwise put on a line of its own; and `.form__hint` / `.optional` are spans INSIDE a label, so they win by being direct rules rather than inherited ones. **Fields stack, one after another** — `.form__grid` is a single 24rem column, not the auto-fit grid it was. The grid packed fields by available width rather than by meaning, so which field sat beside which changed with the viewport AND with the result type (Unit landed next to a checkbox on one render and next to Date on the next); a single column reads in the order the fields were written, which is the order you fill them in. Each field fills the form's own width, so the CONTAINER sets the measure rather than a number in the stylesheet — a dialog gives a comfortable one, a full-width page card a wide one. `.form label` is `row wrap` rather than `column` so a label's text node and its "(optional)" span stay on one line — with a column each optional field cost an extra line — and a flex-basis rule pushes every CONTROL to its own full-width row beneath. `.form__primary` (an event's Title, rendered above the grid) is full width like the rest; only its input size marks it as primary. Submit/Cancel join the shared plate via `.form__actions button`. `.form__editing` ("New event", "Editing the 2026-06-18 reading") became the ruled section head. **Inside a modal the form drops its panel** (`.modal__body .form`) — the dialog is already the container, and the two nested boxes read as a card inside a card. The modal itself squares to 4px with a serif title (a dialog is a small page). Two copy fixes went with it, both pre-existing inconsistencies the restyle made obvious: the submit button said "Add observation" while the dialog, the rail button and the rest of the app say "reading"; and the add modal carried BOTH a labelled "Or import from PDF" divider and an "Import from PDF" heading 40px below it, so the divider lost its label and the heading became the ruled section head. **Profile** joins the grouped serif page-title rule and turns each section (Demographics / Height / Weight) into a ruled `.rsec__head` whose hairline runs out to its one action — the heading takes `flex: 1` so the button lands at the right margin, the same shape as the metric rail's. Those actions, plus the timeline's kind filters and sort, now share ONE **small-plate** rule: the large buttons' squared plate scaled down, for controls that sit beside content rather than heading it. Their height is the **`--ctl-h` token**, not their padding, and their spacing the **`--ctl-gap`** token; the collapsing search field and the Documents type filter take both: an input's line box is taller than a button's at the same font size, so three controls each sized by their own content came out three different heights on one row (measured 27.19px for all of them now). The small-plate selectors are **direct-child** (`.records__head > button`) for a related reason — `SearchField`'s magnifier and × are buttons inside those same heads, and a descendant selector was giving them the plate's uppercase, border and padding. The saved demographics render as the shared labelled-fact rows (`.stat__k` type over a hairline), and the current weight/height uses `.stat__k` / `.stat__hero` / `.stat__big` outright rather than a bolded sentence starting with "Current:" — which is what made it a markup change and not only CSS. **Mono is for FIGURES, and Profile is where that line had to be drawn explicitly**: the date of birth takes it (via a `--num` modifier on its row) and "Male" beside it does not, because a word set in the figure face reads as a code. The `.segmented` sex control was a grey track with a raised white thumb — a THIRD idiom for a choice the chart's Linear/Log switch and the timeline's view toggle already share — so it became that same hairline box with the active segment filled. One container decision worth noting against the "fields fill their form" rule: `.profile__form` (the inline weight entry) caps itself at 24rem, because a number, a unit and a date do not want the width of a full-page card — that's the container setting its measure, which is exactly where that decision belongs. Profile's tabs are now **Profile · Conditions & medications · Immunizations · Collections** — the whole permanent record in one place. Immunizations was the last `ComingSoon` stub (a nav entry advertising an empty room); it now holds real records, so the stub component, its styles and its probe entry went with it, and `/immunizations` redirects to the tab exactly as `/conditions-medications` does. Immunizations also carry a Timeline kind (indigo `#5f3dc4`, ordered after `event` and before `collection`), whose entry shows the vaccine, then a dose · site line rendered ONLY when one of them exists — a bare "vaccine, date" record shouldn't get an empty second row. **Every form in the app is now an OVERLAY** (`Modal`), not an inline block: an inline form pushes the list or chart it is about down the page, so adding a record hides the records you were reading, and on the Timeline it reflowed a page whose headers are already sticky. It also removed a workaround — the conditions/medications forms had `scrollIntoView` refs whose only job was to drag the page to a form that could be nowhere near the row it belonged to. Two form headings changed with the move: `EventForm` and `ObservationForm` printed "New event" / "Editing the <date> reading" at the top, which the dialog header now says — so each keeps only the part the header CAN'T say (which event, which date), since the row it came from is behind the overlay. `.modal__body .profile__form` also lifts the weight form's 24rem cap, which inside a 640px dialog left a column of dead space. The panel reuses the conditions pattern wholesale: ruled head, one action opening one form in two modes, two-step delete. Its table is `table-layout: fixed` with declared column widths: with eight columns the auto layout gave a two-word Site cell the same width as a Notes sentence, so the VACCINE NAME — the thing you scan by — was the one that wrapped. It also carries the shared collapsing **`SearchField`** (`components/shell/SearchField.jsx`), which is now the app's ONLY search control — the Documents page's inline copy was folded into it, having already drifted (one Escape cleared the picked document, the other didn't). **It animates open**, and that is why every part of it is mounted at all times with open/closed carried as a class: the first version swapped a button for a field, and there is nothing to transition between two different elements. The collapsed field is `width: 0` — which needs `min-width: 0`, since a flex item's minimum is its intrinsic width and it otherwise stuck at ~23px — and the container's `gap` is 0, spacing riding on each item's own margin, because a flex gap applies between zero-width items too and would reserve dead space beside the collapsed button. **ONE button carries both states**: the magnifier TURNS INTO a cross on expansion (`CloseIcon`, drawn to the icon module's convention rather than the typed `×` it replaces, whose weight came from the body font and never matched the magnifier beside it) — there is no separate close button, because the magnifier was already the toggle in both directions and a second control doing the same job is the duplication this pass removes. Both glyphs are always rendered, stacked absolutely in one box and cross-faded through a quarter turn: one icon SWAPPED for another can't be animated, for exactly the reason the expansion couldn't be. That margin is **`--ctl-gap`**, the same token the surrounding toolbar uses between its own controls — the space from the section rule to the button, button to field, and field to `+ Add immunization` is ONE measurement (12px, measured), not three that happen to look alike; a field growing between them makes any mismatch visible mid-animation. The field can't read its container's flex `gap`, which is why both read the token. The result-count span is `:empty`-guarded rather than unmounted when a caller passes no count — an empty span still claimed its margin, making the one gap between the field and the button after it double every other gap on the row, while unmounting it would cost the count its fade-in when it does arrive. Filtering is in the browser across every text field including LOT and NOTES — "which shot was lot 9549B" and "which came from the childhood card" are exactly the questions a vaccination record gets asked — because the whole list is already loaded and a search endpoint would be a round-trip to re-send what the page is holding. Its date column is mono like every tabulated date, but the **"Date unknown" placeholder inside it stays prose** — it is a statement, not a date, and setting it in the figure face would make an absent date look like a value. The vaccine field is a free-text `datalist`, not a select: a record can name a travel vaccine, a brand or a trial product, and a closed list that can't hold what your card says is worse than no list. **The image is FITTED IN JS, not by CSS**, and that is a correctness fix, not a preference. The canvas sat in a shrink-wrapping flex frame under `max-width/max-height: 100%`, and flex's default `align-items: stretch` forced it to the frame's CLAMPED height while leaving its width alone — so any image taller than the stage was **squashed**: a 512×1024 coronal rendered 512×748, 27% short, with every measurement on it wrong in one axis. Eight series in this record are taller than wide (up to 1248×1969) and every bundled sample DICOM is square, which is why only a TALL fixture could catch it — the harness seeds one now. Each CSS repair fails somewhere: `align-items: flex-start` keeps the aspect but loses the clamp (the image overflows), `aspect-ratio` does not back-propagate a max-HEIGHT into the width, and `object-fit: contain` fixes the picture while breaking everything else — every pointer mapping here (clicks, the zoom anchor, the filter test) reads the canvas's BOX, which would become a letterbox rather than the image. So a ResizeObserver on the stage computes `min(stageW/cols, stageH/rows, 1)` and the frame is sized to that box in pixels; the `min(…, 1)` preserves the existing rule that an image is never blown up past its own resolution. **`crisp` is now DERIVED from that same fit** rather than measured by a second observer on the canvas: that observer watched a box the fit was about to change, so it ran a render behind and chose the filter from the PREVIOUS size — observed picking the magnifying filter for a 512-wide image displayed at 374.

**Imaging is a DRAWER + an INSTRUMENT** (layout B2, chosen from mockups). Choosing a series is a navigation act, and this record is six studies carrying up to 94 series each — a long index to keep on screen while reading an image — so closed, the viewer gets the FULL page width (~55% more image area). It opens itself when nothing is selected yet, which is the one moment the picker IS the page; a deep link (`/imaging?study=…`) arrives with a series chosen and so opens straight onto the images. It overlays rather than displaces, so opening it never resizes the image — the same rule every control on this page follows. **The stage and its controls are ONE bordered unit** (`.dcm__instrument`) rather than a picture with widgets loose beneath it, and that unit carries its OWN palette in BOTH themes. That is the existing stage rule extended: the stage has always been pure black in either theme because it is the image's own ground, not the app's chrome — and a light control bar under a black stage was the brightest thing on a page whose whole job is reading greys. The buttons keep the app's small plate exactly (shape, type, `--ctl-h`); only the colours belong to the console. The strip is TWO rows: slider + series/slice readout, then tools · status · window controls. **The status now sits between two fixed flanks** and takes the slack, which is what stops a measurement appearing from reflowing the row — the old fix was a hardcoded `min-height` on a status line that always rendered, i.e. the layout problem solved by reserving space rather than by removing the reflow. **The viewer goes FULLSCREEN** (the `⛶` tool, or `F`), and it fullscreens the **instrument**, not the page: every control you need while reading — slider, tools, presets, W/L, the slice readout — lives inside that unit, so it IS the viewer. The harness gained `--click SELECTOR` for this, since a state behind a control was previously unreachable from it.

**A DARK THEME**, chosen in Settings → Display (System / Light / Dark). It works because the pass above finished the token layer: every ground, border and semantic colour is a variable, so the theme is one `:root[data-theme='dark']` block restating them — no per-component dark rules anywhere. Three things it forced, each a decision rather than a colour pick:

- **Grounds had to be split out.** Panels hardcoded `#fff` and pages `#f8f9fa` — precisely what a theme moves — so they became `--c-surface` / `--c-surface-2` / `--c-page` and a 132-declaration sweep took every remaining literal onto a token. **That sweep left one trap, and the Timeline fell into it**: a STICKY MASK must name the ground it masks. The timeline's topbar, its month headers, the calendar's year labels and the spine-dot halo are opaque only so entries scroll cleanly underneath them, and they all named `--c-surface-2` — which is the SAME value as `--c-page` in light, so the mistake was invisible, and a LIGHTER quiet-fill in dark, where the bars came out as bands a shade off the page behind them. They name `--c-page` now (verified: topbar, month strip and page ground all render `rgb(17, 22, 27)` in dark). The lesson generalises — two tokens that happen to be equal in one theme are not interchangeable, and the theme they differ in is where you find out. The imaging stage stays pure `#000` in both themes: it is not chrome, it is the image's own ground, and a radiologist's black is not a theme choice.
- **The accent inverts its JOB.** On white, graphite is the darkest thing on the page and a filled graphite plate is the loudest control; on near-black that same graphite is invisible. Dark lifts it to a pale slate — still "this is the app talking", now light-on-dark — and `--c-accent-soft`/`--c-accent-line` flip from a tint ABOVE white to a lift ABOVE black.
- **The semantic colours became tokens, deliberately amending the rule at the top of index.css.** They keep their MEANING and change their VALUE: out-of-range red on `#fff0f0` is unreadable on a dark panel and the reference band's pale green vanishes outright, so each gets a lighter ink and a very dark, barely-tinted fill. Red is still red; it is a red that can be read. What still must never happen is a PALETTE change moving them.

**The Linear/Log switch is REMEMBERED** (`prefs.js` → `ht-chart-scale`, browser-local like the theme): switching to log is a way of LOOKING at a record you come back to, and re-choosing it every visit made it feel like a novelty rather than a view. Two decisions hold it in place. It is ONE GLOBAL SCALAR, deliberately not per-metric — per-metric would mean writing a map of metric NAMES into browser storage, and the set of labs someone tracks is record-adjacent in a way "log" is not (`ht-last-metric` already stores one name for a concrete need; this is the reason not to grow it into a set). And what is stored is the PREFERENCE, while whether it APPLIES is DERIVED per chart — `logScale = pref === 'log' && logWorthwhile` — so a remembered "log" can never reach a chart that never offered the choice. That derivation is what keeps the weight chart (all-positive, so `canLog`, but a narrow ratio) linear, with no reset anyone has to remember to perform; it also made the old `logWorthwhile || logScale` clause in `showLogToggle` dead, since log now implies worthwhile. **Zero is labelled whenever the axis reaches it**, and that took two changes because it was failing for two reasons. Whether a linear axis is zero-based is the first thing a reader needs from it — it decides whether a doubling LOOKS like a doubling — so 0 is added explicitly when `inDomain(0)` rather than left to whichever tick list happens to produce it, and it outranks everything else. It then has to SURVIVE: ALT's band bounds are 0 and 10 on an 800-unit domain, two ticks a few pixels apart, and Recharts (whose default `interval="preserveEnd"` hides labels it judges to collide, keeping the later one) was silently dropping the 0. So the crowding is arbitrated HERE, in priority order — 0, then the meaningful reference values, then the round fillers, each admitted only if it clears `MIN_TICK_GAP_FRAC` (5% of the domain, ≈14px in the ~266px plot) of every tick already kept — and the YAxis takes `interval={0}` so the library renders exactly what it was handed. Neither half works alone: without the thinning, forcing every tick overlaps them; without `interval={0}`, the library vetoes the 0 anyway. The cost is visible and accepted — on a metric whose whole band sits near zero (a 10–40 band under an 850 spike), 0 wins the slot and the band's own bounds lose their labels; the band still draws, and the axis no longer implies it starts somewhere other than zero. A domain that never reaches 0 (Hgb 12–18, creatinine 0.4–1.3) gets no 0 tick, which is the "if it's relevant" half of the rule.

**"Log" is a SYMLOG** (`d3-scale`'s `scaleSymlog`, now an explicit dependency rather than recharts' transitive one) — linear across a small region around 0, logarithmic beyond it. A plain log axis has no position for 0, and a band that floors at 0 is ordinary here (ALT, bilirubin, LDL), so this was worked around three times before being solved: a hard band edge at the clamped floor **asserts a bound nobody chose** (ALT's 0 came out as a green line at 6.25); a **fade means an OPEN bound** in this chart's own vocabulary and 0 is a defined one; an **off-axis chevron marker** is a caret standing in for a number we know exactly. The fourth idea, plotting 0 at ~1e-17, is the one that fails on arithmetic: a log axis positions by exponent, so that is seventeen decades below the data — 20 decades of axis instead of 2.35, ALT's readings squeezed into 8% of the plot height (21px of 266). With a symlog, **0 is a real position and the band simply draws to it** — no clamp, no marker, no legend, and `LOG_PAD_DOWN`/`LOG_FLOOR_BUFFER`/`logFloor` all deleted. The domain then dips a little BELOW 0 (`LOG_FLOOR_AIR`, 4% of the axis's symlog height, found by inverting the transform — a symlog is symmetric about 0, so a negative bottom is a real position rather than a clamp), which is the exact counterpart of the linear path's sub-zero cosmetic floor: a 0-floor band sits ON the 0 line instead of on the frame, and no tick is generated beneath it. **The constant is the smallest positive bound on the chart** (ALT: 10), so the compressed stretch is exactly the part with nothing in it and the readings keep the room — measured 72% of the plot height, against 68% for the plain log axis that couldn't draw the 0 at all. Ticks are `[0, ...logTicks(constant, top)]`: the decades start AT the linear region's edge, which keeps them out of the compressed stretch where they would crowd into a few pixels. The price is one clause in the notice — "spacing is ratio **above the flat stretch near 0**" — because plain "spacing is ratio" would be false near the bottom. The harness seeds a curated threshold on the wide-ratio metric so `ThresholdRail` is exercised on this axis: the rail reads the y-scale directly (`useYAxisScale`), which makes scale + rail the one pairing a chart change can silently break. LINEAR is untouched throughout, and pinned pixel-identical.

**A 0-floor band keeps a buffer beneath it in log mode, and NO TICK is generated inside that buffer.** A band bound at or below zero (ALT, bilirubin, LDL) can't be placed on a log axis — 0 is at negative infinity — so it is clamped when drawn. `logFloor` is where the clamped edge lands (`lo / LOG_PAD_DOWN`) and the domain drops one FURTHER step beneath it (`LOG_FLOOR_BUFFER`), so the band has air under it instead of sitting flat on the axis line — the same thing the linear path's sub-zero cosmetic floor does, expressed as a RATIO because ratio is what distance means here. **The separation between `logFloor` and `yDomain[0]` is the whole of it**: ticks are generated from `logFloor`, NOT from the domain, because generating them from the domain put a gridline inside the buffer, *under* the band — ALT drew a 5 beneath a band edge at 6.25, which read as a bound at 6.25 that nothing had chosen. The linear axis has always worked exactly this way (its ticks start at `Math.max(0, yDomain[0])` while its domain dips below zero); log just wasn't doing it. Two wrong attempts are recorded here because each looked right in isolation: lifting the band WITHOUT moving the tick floor (a false bound under a bogus tick), and clamping to the domain floor so the band ran off the bottom (honest, but no buffer at all — which is what was asked for). A band whose floor is positive is untouched by any of it: `logFloor` equals the domain floor, the bound sits above it anyway, and the render is pixel-identical (verified by diffing the shot).

**A live log axis carries an amber notice** (`.chart__logwarn`, circled-i, in the row WITH the switch): a log axis breaks the one thing a reader carries between every other chart in the app — that vertical distance means amount — so a rise that looks modest can be a doubling. It also says that **0 can't be shown on it**, which is not padding: a band that floors at zero is common (ALT, bilirubin, LDL), a log axis cannot place 0 anywhere — it is at negative infinity — and the result looks like an axis that simply forgot to label its zero. That exact confusion was reported. It is deliberately not the `.metrics__advisory` block, which is for a standing property of the METRIC (NLR is not a standard test); this is a property of how you are currently looking at it, so it is a caption on the control that caused it and it disappears with it.

**The chart is the one thing that can't read a token**: Recharts takes colours as props that become SVG presentation ATTRIBUTES, and an attribute can't parse `var()`.
